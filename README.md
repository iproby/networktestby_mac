# NetWatch 4

Диагностика подключения в терминале для **macOS, Windows и Linux**: живые измерения, объяснение сбоев, постоянная история и отчёт для разбора проблемы. Приоритет — macOS; недоступные системе показатели отображаются явно.

## Запуск одной командой

Текущая версия опубликована в ветке `codex/netwatch-github-launch`. На macOS / Linux:

```bash
curl -fsSL https://raw.githubusercontent.com/iproby/networktestby_mac/codex/netwatch-github-launch/install.sh | NETWATCH_REF=codex/netwatch-github-launch bash
```

Windows, PowerShell:

```powershell
$env:NETWATCH_REF='codex/netwatch-github-launch'; irm https://raw.githubusercontent.com/iproby/networktestby_mac/codex/netwatch-github-launch/install.ps1 | iex
```

Команда определяет платформу, скачивает полный снимок GitHub, создаёт изолированную среду и открывает интерфейс. Для этого варианта нужен Python **3.9+**; Mac с Homebrew может установить его автоматически. Не нужны Git и `sudo`. Первый запуск требует GitHub и PyPI; готовая среда переиспользуется. Приложение получает клавиатуру терминала даже при запуске через pipe.

Можно передать параметры: `... | NETWATCH_REF=codex/netwatch-github-launch bash -s -- --once --json`. `NETWATCH_REF` также принимает тег или SHA для возврата к старому исходному коду; URL самого установщика должен указывать на существующую версию. Относительные пути считаются от текущей папки пользователя.

**Самостоятельные сборки без Python:** `scripts/build_native.py` и GitHub Actions создают исполняемые файлы для macOS Intel/ARM, Linux x86_64 и Windows x64. Установщики `install-native.sh` / `install-native.ps1` проверяют SHA-256, сохраняют предыдущую версию и поддерживают `NETWATCH_ROLLBACK=1`. После публикации соответствующего GitHub Release можно добавить `NETWATCH_RELEASE=v4.0.0` к обычной команде — будет выбран самостоятельный файл. Пока релиз не опубликован, используйте команду выше. Сборки, подпись Apple/Windows и порядок публикации описаны в [docs/RELEASING.md](docs/RELEASING.md). SHA-256 не заменяет подпись издателя.

Из клонированного проекта: `bash install_and_run.sh` на macOS/Linux, `py run.py` на Windows. Сохранены двойной клик `.command` на Mac и `start_diagnostics.cmd` на Windows. После установки пакета доступны `netwatch` и `python -m netwatch`. В примерах ниже `python3 run.py` можно заменить путём к самостоятельному файлу.

## Интерфейс

| Вкладка | Что помогает сделать |
|---|---|
| 1 Обзор | Увидеть состояние, основания и следующие действия; контрольную цепочку, задержку и трафик |
| 2 Проверки | Найти конкретный IP, DNS или сайт с ошибкой; фильтровать и открыть результат |
| 3 Сеть | Проверить маршруты/VPN, адреса, Wi-Fi, норму сети и нагрузку устройства |
| 4 События | Найти начало/конец сбоя, его длительность и число наблюдений |
| 5 Настройки | Выбрать задачу, редактировать цели и HTTP-условия, бюджет, хранение и фон |
| 6 История | Просмотреть SQLite-архив за час, сутки или неделю и основания старого диагноза |
| 7 Диагностика | Запустить качество под нагрузкой, трассировку, HTTP/TLS, DNS/DoH, Wi-Fi, процессы, IPv4/IPv6, MTU, статусы или агента |
| 8 Сравнение | Зафиксировать ДО, самостоятельно переключить VPN/сеть и измерить ПОСЛЕ |

Клавиши: `1`–`8` вкладки, `r` обновить, `p` пауза, `s` download, `e` HTML+JSON, `?` справка, `q` выход. В полях ввода клавиши принадлежат полю; выйдите через Tab. Работают мышь, Tab, стрелки и Enter. В узком терминале карточки перестраиваются, содержимое прокручивается. Цвета зависят от терминала; `NO_COLOR` учитывается.

Настройки применяются между измерениями. «Сохранить профиль» создаёт новый файл. Цели можно добавлять/изменять/удалять непосредственно в интерфейсе; HTTP-условие задаёт точный код и/или текст в первых 4096 байтах ответа. Профили «Общий», «Видеозвонки», «Игры», «VPN» и «Экономия» меняют частоту/набор проверок. Оценка задачи относится к контрольному пути; приложение не получает реальную телеметрию игры или звонка.

## Измерения и границы выводов

- Проверки по слоям: адаптер, маршрут, шлюз, внешние IP, системный DNS, прямой DNS, HTTP и сервисы. Выключенные проверки имеют состояние «нет измерений». В основаниях показаны альтернативные объяснения. Пробел после сна/выключения не считается непрерывным сбоем.
- Успешный TCP handshake даёт задержку; `connection refused` подтверждает ответ узла, но не работу сервиса. Доля неудачных соединений не является потерями пакетов. Шлюз, фильтрующий контрольные порты при рабочем интернете, не объявляется сломанным.
- «Качество под нагрузкой» измеряет idle/loaded latency, p95, джиттер, download и upload. Цель TCP одинакова на этапах. Нагрузки запускаются только вручную; маленькая выборка может не успеть дать достаточно измерений. Это короткий HTTP-тест выбранного сервера, а не проверка тарифной скорости.
- Настоящая UDP-потеря измеряется только через свой настроенный NetWatch-отражатель. Публичный TURN/VoIP-сервис не используется для имитации этой метрики.
- Linux трассирует UDP TTL через непривилегированную очередь ICMP-ошибок; macOS/Windows используют системный traceroute/tracert. Повторные пробы показывают адреса и RTT. Во вкладке диагностики включите «MTR: повторять трассировку» для живой таблицы со средней задержкой, p95 и числом ответов; «Остановить» завершает сеанс после текущей пробы. Молчание промежуточного узла не доказывает потери транзитных пакетов.
- HTTP DNS/TCP/TLS/ожидание первого байта получаются через системный `curl`; без него доступны базовые HTTP-результаты. Прокси/редиректы могут объединять несколько соединений. Сертификат проверяется отдельно по прямому TLS-пути, который может отличаться от пути прокси. Проверка доверия не отключается. Если в чистой системе отсутствуют корневые сертификаты OpenSSL, используется включённый CA-bundle certifi; явно заданные SSL_CERT_FILE/SSL_CERT_DIR сохраняют свою границу доверия.
- Сравнение DNS показывает системные ответы, A/AAAA через прямой UDP/TCP и DoH. Отличия split DNS/CDN не доказывают подмену. IPv4/IPv6 проверяются отдельно; прокси может скрывать семейство конечного сервера. MTU/DF — ограниченный эксперимент; фильтрация ICMP не даёт точного PMTU.
- `403`/`429`, один недоступный сервис или публичный статус Cloudflare/GitHub сами по себе не доказывают сбой провайдера. Статусы запрашиваются только вручную. «Регион» — принадлежность сервиса, а не проверенная география CDN.
- Возможный captive portal обнаруживается по неожиданной странице/редиректу вместо ожидаемого HTTP 204. Кнопка входа открывает обнаруженный HTTP(S)-адрес только по нажатию пользователя. Изменение сервиса или прокси тоже может дать такой результат.
- Норма задержки обучается по здоровым наблюдениям одной сети и совпадающим TCP-целям: минимум 20, до 720 последних значений, медиана/MAD. После перезапуска используется SQLite. Это наблюдаемая норма, а не гарантированный SLA.
- Сравнение ДО/ПОСЛЕ показывает маршруты, DNS, Wi-Fi, доступность общих целей и изменение задержек. Для вывода о причине полезно повторить эксперимент; приложение не переключает VPN и не меняет сетевые настройки.

## CLI

```bash
python3 run.py --once --json                   # один снимок
python3 run.py --plain                         # наблюдение текстом
python3 run.py --profile calls --notify         # профиль и уведомления
python3 run.py --diagnose quality               # download/upload + задержка
python3 run.py --diagnose trace --target 1.1.1.1
python3 run.py --diagnose http --target https://example.com
python3 run.py --diagnose dns --target example.com
python3 run.py --diagnose processes
python3 run.py --diagnose dual --target https://example.com
python3 run.py --diagnose mtu --target 1.1.1.1
python3 run.py --diagnose status
python3 run.py --history 24 --json              # архив за сутки, до 10000 снимков
python3 run.py --report                        # цикл и HTML+JSON
python3 run.py --replay path/to/report.json     # офлайн-интерфейс
python3 run.py --replay path/to/report.json --plain
python3 run.py --capture-label before-vpn      # сохраняет путь к снимку
python3 run.py --compare path/to/capture.json  # измеряет и сравнивает
python3 run.py --list-interfaces
python3 run.py --help
```

Офлайн-просмотр не запускает мониторинг, нагрузку, диагностику или фон. В неинтерактивном терминале он печатает сохранённые снимки. Контекст старых инцидентов из отчёта доступен в истории. Код возврата `0` означает, что цикл выполнен: состояние сети смотрите в `cause.status` и отдельных пробах.

## Фон, уведомления и экономия

```bash
python3 run.py --background start --profile economy --notify
python3 run.py --background status
python3 run.py --background stop
```

Процесс принадлежит пользователю, сохраняет историю и не печатает каждый цикл в лог. PID проверяется вместе со временем создания. Закрытие TUI не завершает отдельно запущенный фон. Фоновый процесс и TUI используют собственные циклы; для общего просмотра фона можно обновлять вкладку истории. Не запускайте множество наблюдателей с одинаковыми целями без необходимости.

Автозапуск при входе регистрируется **явно**: `--service install`; затем `start`, `status`, `stop`, `remove`. macOS использует LaunchAgent, Linux — systemd пользователя, Windows — Task Scheduler пользователя. Нужна доступная сессия соответствующего менеджера служб; установщик приложения службу не регистрирует. Фон/служба используют копию профиля на момент запуска; после изменения настроек перезапустите их с обновлённым профилем.

Уведомление по умолчанию приходит после 3 проблемных циклов, восстановление — после 2 успешных. Параметры `notify_after`, `recover_after` и `maintenance_until` (ISO-дата с часовым поясом) доступны в профиле. Каналы: macOS Notification Center, Linux `notify-send`, Windows toast через PowerShell; отказ разрешения показывается в журнале. После разрыва наблюдений счётчики сбрасываются.

Суточный бюджет тестовых загрузок — 50 МБ по UTC, в профиле экономии — 10 МБ. Резерв учитывает одновременные инструменты и другие процессы NetWatch с тем же каталогом SQLite; после аварии резерв освобождается через 15 минут. Отдельно считаются прочитанный HTTP-payload и число контрольных операций. Ошибка upload консервативно списывает всю попытку. Заголовки TCP/TLS/IP, DNS-пакеты, скрытая буферизация и расход других приложений не измеряются, поэтому это не лимит всего сетевого трафика. При `--no-log` расход хранится только до выхода. Если SQLite-бюджет недоступен, большие тесты блокируются с объяснением.

После 12 здоровых циклов адаптивная пауза удваивается; при работе от батареи — ещё вдвое. `--fixed-interval` отключает адаптацию. Период = время измерения + пауза. Запущенный запрос завершается по своему таймауту, даже если нажата пауза.

## Свои цели и агент

```bash
python3 run.py --write-config my-network.json
python3 run.py --config my-network.json
python3 run.py --once --no-regions --no-direct-dns --dns-name example.com
python3 run.py --http-url https://example.com --public-endpoint '1.1.1.1:443'
```

JSON-профиль валидируется; существующий файл не перезаписывается. Повторяемые CLI-параметры заменяют соответствующие списки. Пустые списки отключают группу; оставьте хотя бы один внешний IP или HTTP-URL. `--interface` меняет адаптер счётчиков, запросы идут по системной маршрутизации.

Свой агент на второй машине:

```bash
python3 run.py --agent --bind 127.0.0.1 --port 8765 --udp-port 8766
python3 run.py --diagnose agent --target http://127.0.0.1:8765
```

Loopback подходит для локальной проверки. Для другой машины нужны **HTTPS, свой сертификат/ключ и одинаковый `NETWATCH_AGENT_TOKEN`** в окружении клиента/сервера. Значение не записывается в профиль или отчёт. Передайте серверу `--bind <адрес> --tls-cert cert.pem --tls-key key.pem`; доверие сертификату на клиенте настройте обычными средствами ОС. Секреты не передавайте в URL или командной строке. UDP вне loopback тоже требует токен; отражатель проверяет HMAC, ограничивает размер/частоту и не усиливает пакеты.

Для своего агента профиль клиента может содержать:

```json
{
  "remote_agent_url": "https://agent.example.com:8765",
  "udp_endpoint": "192.0.2.10:8766",
  "speedtest_url": "https://agent.example.com:8765/v1/download?bytes={bytes}",
  "upload_url": "https://agent.example.com:8765/v1/upload"
}
```

Адрес/домен в примере замените своими. Агент предоставляет только снимок и ограниченные загрузки; не исполняет удалённые команды и не принимает произвольную цель проверки. Bearer-токен передаётся только настроенному origin; перенаправление с него на другой origin запрещено. Давность удалённого снимка показана отдельно; старше 120 секунд — устаревший.

## История и отчёты

Данные сохраняются в `~/Library/Application Support/NetWatch` на Mac, `%LOCALAPPDATA%\NetWatch` в Windows и `${XDG_STATE_HOME:-~/.local/state}/NetWatch` в Linux. `--state-dir PATH` меняет каталог. Установленные версии исходников лежат отдельно: Mac/Windows в `NetWatch/versions`, Linux в `${XDG_DATA_HOME:-~/.local/share}/NetWatch/versions`. `NETWATCH_INSTALL_DIR` меняет кеш установки; старые версии автоматически не удаляются.

SQLite хранит снимки/инциденты/инструменты до 7 дней (настраивается 1–30), примерно до 150 МБ сжатого payload; индексы, WAL и служебные страницы требуют дополнительного места. Очистка выполняется через каждые 100 событий. JSONL дополнительно ротируется: 5 МБ × 4 файла. В живой панели — 240 снимков; архив показывает до 1000 последних записей выбранного периода. При перезапуске старый открытый инцидент закрывается на последнем наблюдении как прерванный.

Экспорт создаёт автономный HTML с графиком/хронологией и JSON с диагностикой. Для последних инцидентов добавляется доступный контекст ±5 минут; будущие наблюдения можно включить последующим экспортом. При больших объёмах контекст ограничен. Экспортные файлы автоматически не удаляются.

По умолчанию адреса/SSID/MAC заменяются устойчивыми в пределах отчёта псевдонимами, query-значения и учётные данные URL удаляются. Это не гарантия удаления всех персональных сведений из произвольного текста/имён целей — просмотрите файл перед передачей. `--raw-report` вместе с `--report` оставляет исходные адреса. `--no-log` отключает JSONL и SQLite, ручной экспорт остаётся доступен. `--log-file` задаёт другой путь JSONL; SQLite остаётся в каталоге состояния.

## Поддержка платформ

| Показатель | macOS | Linux | Windows |
|---|---|---|---|
| Адреса/маршруты/счётчики | route/netstat/scutil + psutil | proc/resolv.conf + psutil | PowerShell NetTCPIP + psutil |
| Wi-Fi | CoreWLAN: RSSI/шум/SNR/канал/скорость; SSID может требовать разрешение геолокации | proc + `iw`, если установлен | Native WLAN: SSID/BSSID/качество/скорости; RSSI/шум/канал пока недоступны |
| Процессы | nettop, когда разрешён | `ss` TCP_INFO для видимых живых TCP-сокетов | подключения/CPU/память; учёт байтов ETW пока недоступен |
| Задержка/сайты/DNS | Да | Да | Да |

Linux-счётчики процессов не включают UDP, закрытые и совместно используемые сокеты; это частичная выборка. Отсутствующие байты не подменяются дисковым I/O. Для системных инструментов могут требоваться дополнительные разрешения. Split tunneling без default route и системный/браузерный прокси могут отличаться от наблюдаемого пути. iOS/Android и отдельный GUI-клиент не заявлены как поддерживаемые платформы.

Нативные macOS/Windows проверки следует выполнить на соответствующих машинах: Linux-тесты и fixtures их не заменяют.

## Разработка

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e '.[test,build]'
.venv/bin/python -m pytest -q
.venv/bin/python -m pip check
.venv/bin/python scripts/build_native.py
```

Windows использует `.venv\Scripts\python`. Тесты запускают собственные временные HTTP/UDP/TLS/DoH-серверы и проверяют реальные измерения, авторизацию, бюджет, восстановление истории, обезличивание, фон и действия Textual. Публичные сайты для тестов не нужны. CI: три ОС, Python 3.9/3.12; сборки исполняемых файлов — отдельно. Список критериев и проверенных ограничений: [docs/NETWATCH_4.md](docs/NETWATCH_4.md).
